## P18-S1: starting a bot in a given folder

### The route
`POST /api/bots/<botId>/tasks` creates a conversation ("task") for a bot. The handler reads:

- `title` (optional), `select` (optional boolean: `false` leaves the bot's open conversation as it is)
- `cwd` (optional). When it is present:
  - the caller must hold the admin scope, else `403 "Choosing a working folder requires the admin scope"`
  - it must be an absolute path to a folder that exists, else `400 "working folder must be an
    absolute path"` / `"that folder doesn't exist: …"` / `"that path is not a folder: …"`
  - `~` and `~/…` are expanded
- `approvalMode` (optional): only `ask` or `full`. `full` is refused for this kind of caller, so
  Chorus leaves it out and the conversation follows the bot's own approval setting.

**Where a turn then runs:**
- A conversation made with `cwd` keeps that folder for every turn.
- One made without `cwd` pins the bot's default folder at its first turn.
- Either way, the bot's own default folder is untouched. So Chorus can give each hand-off its own
  worktree without moving the bot.

The CLI has no folder option. `send` takes `--task new|current|ID` and `--title`, and `new-bot`
takes a name, title, team and model only. So the folder is only reachable through the HTTP API (or
MausBot's own screens).

### Sending the hand-off message
`POST /api/bots/<botId>/messages` with `{ text, threadId, sendId? }`. MausBot's own MCP server uses
this for `send_bot_message`.

- `threadId` names the conversation made above.
- `sendId` (16–80 letters, digits, `-` or `_`) makes a repeat with the same id a no-op, so a retry
  never sends twice.

The reply reports the message id, or that it was queued behind running work. Client scope is
enough.

### Who may call what (the desktop app)
Read from the request-authentication code, and checked live where it costs nothing:

- **Loopback reads need no token.** A request to `127.0.0.1` with no browser headers
  (`sec-fetch-*`), and no `Origin` or a loopback one, gets the owner's scopes (`admin`, `client`).
  - *Live:* `GET /api/health` and `GET /api/bots` answered 200 with no token.
  - The bot list includes each bot's `id`, `name`, `title`, `cwd`, `busy` and `activity`, and its
    conversations (`tasks`) with `threadId`, `title`, `cwd`, `busy`, `activity` and `updatedAt`.
  - That is enough to pick a bot and to watch a conversation, without a token.
- **Every write needs a token on the desktop app.** Any `POST`, `PATCH` or `DELETE` without the
  desktop app's own secret header is refused with `403 "forbidden: this change must come from the
  desktop app or a paired device"`.
  - *Live:* an unauthenticated `POST /api/bots/<id>/tasks` answered 403.
- **Tokens:**
  - A token is sent as `Authorization: Bearer omb_sess_…`, where `omb_sess_` is followed by 43
    URL-safe base64 characters (32 random bytes). Scope `client` can chat and answer approvals;
    `admin` can also change settings, including a conversation's folder.
  - It lasts at most the server's session limit (180 days by default) and never renews. Listed with
    `openmausbot token list`, and revoked with `openmausbot token revoke ID`.
  - **The CLI path probably doesn't work against the desktop app.** The CLI's
    `openmausbot token create NAME --out FILE [--scope client|admin] [--expires 90d]` mints in two
    steps: `POST /api/auth/pairing` makes a one-time pairing code with the scopes, then
    `POST /api/auth/pair` redeems it into a token. The first is a write, and the desktop app
    refuses writes that don't carry its own secret (above). So that first step probably fails on
    the desktop app; this was read, not run.
  - **Redeeming a code does work from loopback.** `POST /api/auth/pair` is exempt from that rule.
    It takes JSON `{code, label}` and answers `{token, session}`, with the session's `scopes` and
    `expiresAt`. A wrong code is a 401, and repeated wrong codes lock the caller out for a while
    (429).
  - So a pairing code that Matthew makes in MausBot (Settings → Phone & devices, a 12-character
    code like `7KQ2-M9XD-H4TP`) can be redeemed by Chorus directly. The token then never passes
    through the clipboard, a file or the CLI.
  - *Live:* `token list` reported no tokens. Making a token was stopped by the session's permission
    policy, so nothing was minted.

### What this means for P18
1. **Chorus needs one MausBot token** to start a hand-off by itself. It needs admin scope, because
   only admin can pin the conversation to the `maus/…` worktree. Chorus gets it by redeeming a
   pairing code Matthew makes in MausBot (§4). The token is stored as a DPAPI credential, like the
   Telegram token, and sent only in the `Authorization` header to `127.0.0.1`. It is never written
   to argv, a log, the note or an export. The scrubber learns its shape (`omb_sess_` and 43
   characters).
2. **Without a token, Hand to MausBot still works by hand.** Chorus makes the worktree and writes
   the note, then shows the folder and a ready-to-paste message for Matthew to start the
   conversation in MausBot himself. It says why (fail visible).
3. **Chorus can watch without a token.** It finds the conversation by `threadId` in `GET /api/bots`
   and reads `busy`, `activity` and `updatedAt`. That gives the banner's "last changed" without
   ever opening MausBot's files.
4. **Choosing a bot:**
   - The bot list comes from `GET /api/bots`.
   - The default is the bot whose folder is the project's folder, or the last one used for that
     project.
   - Matthew's own bots are already set up one per project, which fits.

## P18-S2: MausBot as an MCP client (deferred with 18.4)

Read from the MCP registry code, not run.

- **Kinds of server:** user-added servers are `stdio` (`command`, `args`, `env`) or remote: `type:
  "http"` (Streamable HTTP, the default) or `"sse"`, with `url` and `headers`.
- **Credentials:** these belong in `headers`; MausBot refuses them in the URL. Values can be kept
  as `vault:<id>` pointers in MausBot's own vault.
- **Who gets a server:** a server can belong to one bot (`bot`), or bots can allow-list servers by
  name.
- **When changes apply:** adding a server through MausBot's screens or API applies at once, with a
  health check. A hand edit of its settings file needs a restart.

So 18.4's design holds: a loopback `POST /mcp/mausbot` with a bearer token in a header. Running it
live means adding a server to MausBot, which waits for 18.4 and Matthew's go-ahead.

## P18-S3: a bot writing its own entry

Not run, because it needs the test bot to run turns.

The note format (plan §4.1) is plain Markdown with labelled lines, so a bot can follow an
instruction such as "before you finish, add an entry at the top of `.chorus/handoff.md` with Done,
State, Open and Next". Whether it does so reliably is a live question.

P18 treats the bot's entry as optional:
- When the baton comes back, Chorus writes its own entry from git (commits ahead of the base,
  files changed) if the newest entry isn't the bot's.
- The return card shows which kind it is.

## 4. Waiting on Matthew

How Chorus gets its MausBot token. Options, with what each leads to:

- **(a, recommended) Pair Chorus like a device.** Matthew makes a pairing code in MausBot
  (Settings → Phone & devices) and types it into Chorus's Settings → MausBot. Chorus redeems it
  (`POST /api/auth/pair`, label "Chorus") and keeps the token as a DPAPI credential. If the code
  carries full access (admin scope), Chorus starts each hand-off in its own worktree with no manual
  steps. The token lasts up to 180 days; Matthew pairs again when Chorus says it has expired.
  Full access means the token could also change MausBot's settings. Chorus only ever calls the
  four routes above, and the device can be signed out in MausBot at any time.
- **(b) A chat-only pairing (client scope).** Chorus could send messages but not choose the
  folder. Each hand-off would then start by hand: Chorus shows the folder and the message to paste.
- **(c) No pairing.** Same as (b) for starting, and Chorus only watches.

Chorus accepts an `omb_sess_…` token in the same field. A token made elsewhere, such as by
`token create` against a served workspace, works too.

The live S1 run (make the "Chorus test" bot, start it in a scratch worktree, send a message, see it
work there) and the live S3 run follow once a token exists.
