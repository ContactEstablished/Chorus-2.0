# P15 spikes: unattended permissions, allowances, agent tools, Telegram

Slice 1 of [HANDOFF-P15-loop.md](../HANDOFF-P15-loop.md), run 2026-10-25 before any product code.
Versions: Claude Code 2.1.308 (2.1.310 after the terminal check, see S1), codex-cli 0.163.0,
opencode 2.1.4. Every probe ran in a scratch
folder outside any repository, with tiny turns: Claude Code (Haiku) and Codex on subscription,
opencode on its free, keyless `opencode/deepseek-v4.1-flash-free`. OpenRouter spend: $0. Raw
evidence and the throwaway harness are in `_verify/p15/`.

| Spike | Question | Result |
|---|---|---|
| P15-S1 | Do unattended builders refuse what isn't allowed, without prompting? | **Pass** for Claude Code, in print mode and in a terminal in Chorus's PTY; **pass** for Codex in exec mode |
| P15-S2 | Where do the subscriptions report their allowance? | **Pass**: Claude Code's `rate_limit_event` (print mode) and its status line input (terminal); Codex's `account/rateLimits/read` |
| P15-S3 | Can each CLI call Chorus tools on a loopback MCP endpoint, with the token kept out of argv? | **Pass** for all three; a tool call must not be held open (Claude Code gives up after about 60 s) |
| P15-S4 | Telegram long polling and buttons from Windows | **Pass**, run in slice 4 on the built relay with a dev bot: pairing, buttons, replies, commands, offline and 409. A first TLS connection can be reset, so connect errors are retried |

## P15-S1: unattended permissions

### Claude Code

Measured with `-p --output-format stream-json`, which reports each refusal as a `system` message
with `subtype: "permission_denied"` and lists them again in the result's `permission_denials`.

With `--permission-mode dontAsk --allowedTools "Edit(./**)" "Bash(node --version)"`:

| Attempt | Result |
|---|---|
| Write a file in the working folder | Allowed |
| Write `../outside.txt`, `.claude/settings.json` or `.git/hooks/pre-commit` | Refused, no prompt (`decision_reason_type: "mode"`) |
| Read a file outside the working folder | Refused, no prompt |
| `node --version` (listed) | Allowed |
| `curl`, `git init`, `npm --version` | Refused, no prompt |
| `node --version && node -e "<write outside>"` | Refused: each part of a compound command must be allowed |
| `whoami` (not listed) | **Allowed**: Claude Code passes commands it classes as read-only |
| `echo hi > file` in the working folder (not listed) | **Allowed**: the redirect is covered by the edit rule |

So the allowlist bounds what changes, not every command that runs. The refusal text also tells the
model "You *may* attempt to accomplish this action using other tools", so a builder's prompt must
say to call `ask` instead of working around a refusal.

Adding `--restricted --tools "Read,Edit,Write,Glob,Grep,Bash"` (new in 2.1.308) changed three
things, all wanted for a builder:

- Only the named built-in tools exist. Without it a session also had `WebFetch`, `WebSearch`,
  `PowerShell`, `Task`, cron, `RemoteTrigger`, `Workflow` and worktree tools.
- User, project and local settings files are ignored, so Matthew's own `SessionStart` hook didn't
  run. `--settings` still applies, which is how Chorus passes its hooks.
- File tools are confined to the working folders: a read outside it fails as "outside" the
  working directories, not as a permission question.

**The account's claude.ai connectors (four on this machine) load into every session, `--restricted`
included.** Only `--strict-mcp-config` with an `--mcp-config` file removes them.
With all of these flags, the session's tools were exactly the six named ones plus Chorus's own.

**Builder launch, proposed:** `--restricted --tools "Read,Edit,Write,Glob,Grep,Bash"
--permission-mode dontAsk --allowedTools "Edit(./**)" "Bash(<each check command>)"
"mcp__chorus__<each tool>" --strict-mcp-config --mcp-config <file in app data>`, plus Chorus's
usual `--settings`.

**In a terminal**, the same launch ran in the `p15` instance's PTY, started from a `shell` session in a
fixture folder. Claude Code trusts `%TEMP%\chorus-p15`: Matthew agreed, and the trust prompt was
answered "Yes" once there, so every fixture and worktree under it inherits the trust. The footer read
"don't ask on". Asked to write a file, run `curl`, `git init` and `node --version`, and write outside
the folder, it did the first and the fourth; `curl` and `git init` were refused without a dialog (none
in about ten samples of the screen), and the outside write was refused by `--restricted`.

**Side effect:** started from a plain shell, outside Chorus's launch path, Claude Code had no
`DISABLE_AUTOUPDATER=1` (L7) and updated itself to 2.1.310 during the check. 2.1.310 still lists
`--restricted`, `--strict-mcp-config`, `--tools`, `--allowedTools`, `--mcp-config` and `dontAsk`. A
probe started outside Chorus must set L7's switches itself.

### Codex

`codex exec --json -s workspace-write` (exec mode never asks):

| Attempt | Result |
|---|---|
| Write in the working folder, `git init` there | Allowed |
| Write outside it, with node or PowerShell | **Refused** (`EPERM`, "Access to the path … is denied") once the temp exception is off; **allowed** under `%TEMP%`, because `workspace-write` also makes the temp folder writable by default |
| Read a file outside it | Allowed: `workspace-write` confines writes, not reads |
| Network (`curl`, node `fetch`) | Refused (`EACCES`) |

The machine's Codex config sets `[windows] sandbox = "elevated"`. Builders' worktrees aren't under
`%TEMP%`, so the default is acceptable; `-c sandbox_workspace_write.exclude_tmpdir_env_var=true`
closes the temp exception if needed. A worktree's git metadata lives in the main repository, outside
the workspace, so a Codex builder can't commit. That fits the plan, where the orchestrator does the
git work.

## P15-S2: allowances

**Claude Code** reports both windows in print mode, after the first reply:

```json
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":<unix s>,
 "rateLimitType":"five_hour","overageStatus":"rejected","isUsingOverage":false,
 "unifiedWindows":{"five_hour":{"utilization":0,"resetsAt":<unix s>},
                   "seven_day":{"utilization":0.23,"resetsAt":<unix s>}}}}
```

`utilization` is a fraction (0.23 is 23%). The status line's input documents the same data as
percentages, "only present for subscribers … after first API response": `rate_limits.five_hour` and
`rate_limits.seven_day`, each with `used_percentage` and `resets_at`, and `spend_limit` behind a
gateway. In a terminal, a status line command in a `--settings` file (which `--restricted` still
reads) received `{"rate_limits":{"five_hour":{"used_percentage":1,"resets_at":<unix s>},
"seven_day":{"used_percentage":23,"resets_at":<unix s>}}}` after the first reply, with no
`rate_limits` before it, beside `model.id`, `cost`, `context_window`, `session_id` and
`transcript_path`. What `StopFailure` carries when a limit is
hit was not measured: no limit was reached.

**Codex** answers `account/rateLimits/read` on its app-server:

```json
{"rateLimits":{"limitId":"codex","primary":{"usedPercent":0,"windowDurationMins":10080,
 "resetsAt":<unix s>},"secondary":null,"credits":{"hasCredits":true,"balance":"…"},
 "spendControlReached":false,"planType":"…","rateLimitReachedType":null},
 "rateLimitResetCredits":{"availableCount":…,"credits":[{"title":"Full reset", …}]}}
```

This plan has a single weekly window. The account can also hold **credits and free "full reset"
credits**. Matthew allows no Codex spending beyond the subscription (D98), so the loop must stop a
Codex role before its window runs out, and never spend credits or redeem a reset. Whether Codex
draws on credits by itself at the limit is unknown; slice 9 treats a falling credit balance as a
stop.

## P15-S3: agent tools on a loopback MCP endpoint

A throwaway streamable-HTTP server (JSON responses, a per-run bearer token, tools `ask` and
`task_done`). Each CLI got the token only through the environment variable `CHORUS_RUN_TOKEN`; it
appeared in no argv, config file or output.

| | Claude Code | Codex | opencode |
|---|---|---|---|
| How it's configured | `--mcp-config <file>`: `{"type":"http","url":…,"headers":{"Authorization":"Bearer ${CHORUS_RUN_TOKEN}"}}`, expanded from the environment | `-c mcp_servers.chorus.url="…"`, `-c mcp_servers.chorus.bearer_token_env_var="CHORUS_RUN_TOKEN"` | `OPENCODE_CONFIG_CONTENT`: `{"mcp":{"chorus":{"type":"remote","url":…,"headers":{"Authorization":"Bearer {env:CHORUS_RUN_TOKEN}"}}}}` |
| Approval | The tools must be in `--allowedTools` under `dontAsk` | Exec refused both calls ("requires approval, but approval policy is never") until `-c mcp_servers.chorus.default_tools_approval_mode="approve"` (one of `auto`, `prompt`, `writes`, `approve`) | None asked in `run` |
| Requests seen | `server/discover` (answered "no such method", harmlessly), `initialize`, a GET (405), `tools/list`, calls | `initialize`, a GET, `tools/list`, calls, a DELETE at exit | `initialize`, a GET, `tools/list`, calls |
| How the model calls a tool | `mcp__chorus__ask` | `mcp_tool_call` item | Code mode: one `execute` tool running `await tools.chorus.ask({…})` |
| Arguments | class, question, options and default all arrived intact | Same | Same |
| A call held for 90 s | **Failed: "The operation timed out."** after heartbeats at 30 s and 60 s | Waited, then answered | Waited, then answered |

**Consequence for the design:** `ask` never holds the call while waiting for Matthew. It records the
question and returns at once ("asked; end your turn, the answer comes as your next message"). The
orchestrator then delivers the answer, or a timed default, as the session's next prompt through the
normal delivery path. That works the same on all three CLIs, and a question survives Chorus
restarting.

**Found on the way:** opencode 2.1.4's `run` worked in the folder named by an inherited `PWD`
variable, not in the directory it was started in. It ran git in that folder and read its
`CLAUDE.md` (read-only). Chorus's child environment is an allow-list without `PWD`
(`chorus-core::env::BASELINE`), so its launches are safe; `PWD` must never join that list.

## P15-S4: Telegram (run in slice 4)

The spike needed a dev bot's token in the `p15` instance, entered through the app's UI (decision
11), so it ran in slice 4 against the relay as built, on Bot API 10.3 over `reqwest` with Windows'
TLS (Schannel). Matthew made the bot with BotFather, entered its token in Settings → Phone and paired
his phone; every phone action below was his, on 2026-10-25.

- **Reaching Telegram.** His first Save failed with "error sending request". Telegram was reachable,
  but with Windows' own curl (Schannel) a first TLS connection to `api.telegram.org` was reset and
  the next ones succeeded. A connect error carries no request, so the client now tries it twice
  more, names the innermost cause, and says the token wasn't checked (P15-L12). A made-up token then
  got Telegram's own 401 every time.
- **Pairing and strangers.** `/pair <code>` paired his phone; a message he sent before pairing was
  dropped and audited (`dropped-notpaired`). Groups, other bots and forwarded messages are covered
  by the no-network test only.
- **Loop messages.** Two scripted F1 runs (`make-f1-script.mjs --question --phone`, no model)
  carried four questions, a silent finished phase, three milestones, DONE, and a STOPPED from a stop
  condition (a third, stuck run). The STOPPED text names the failing check and the last good tag,
  without a path.
- **Answers.** Option buttons answered two questions and "…and make it a rule" a third (the rule
  reached the run's `decisions.md`); a Telegram reply answered the fourth. Each sent card was edited
  to show the answer, without buttons. A plain message that wasn't a reply got a hint; it now names
  the open question and how to reply.
- **Commands.** `/status`, `/pause`, `/resume`, `/approve` and `/stop` each did what they say. A
  used Approve button stayed on its milestone and the last milestone had none; every milestone now
  has one, and an approved or stopped milestone is edited to say which, without the button.
- **Offline.** Started with `HTTPS_PROXY` pointing at a closed local port, Settings → Phone showed
  "Offline, retrying: couldn't reach Telegram: … actively refused it (os error 10061)". Opening a
  CONNECT-only tunnel on that port (it sees `api.telegram.org:443`, never the URL) brought it back to
  Connected within the backoff, without a restart, and queued messages went out through it.
- **409.** A second instance (its own identifier, a copy of the test database) polling the same
  bot put both into "Another program is reading this bot's messages (Telegram's 409)"; the first
  was Connected again about 10 s after the second stopped.
- **The token.** A scan of the instance's data folder, `_verify` and this session's task output (223
  files) for anything shaped like a bot token, counting only, found none.

## Proposed lessons

- **P15-L1 — Claude Code 2.1.308 under `dontAsk` still runs read-only commands and in-folder
  redirects that aren't listed, and its refusal invites "other tools".** An allowlist bounds changes,
  not every command; tell an unattended agent to ask instead of working around a refusal.
- **P15-L2 — A Claude Code session gets the account's claude.ai connectors unless
  `--strict-mcp-config` is passed with an `--mcp-config` file,** `--restricted` included.
- **P15-L3 — Claude Code 2.1.308 gives up on an MCP tool call after about 60 s;** Codex 0.163.0 and
  opencode 2.1.4 waited at least 90 s. Never hold a tool call open for a person.
- **P15-L4 — Codex 0.163.0's `workspace-write` on Windows confines writes but not reads, blocks
  network, and also makes `%TEMP%` writable.** A probe under `%TEMP%` looks unconfined.
- **P15-L5 — opencode 2.1.4 takes its folder from `PWD` when it is set,** over the directory it was
  started in.
- **P15-L6 — Claude Code's status line input carries `rate_limits` (percent used and reset time per
  window) once the session has had a reply,** in 2.1.308 under `--restricted` too, so a terminal session
  reports its allowance without print mode.
