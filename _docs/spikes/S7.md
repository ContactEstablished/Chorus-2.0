# S7 — 3D startup splash

**Verdict: pass on every measurable criterion; waiting for Matthew's look** before it counts as done
(he asked for "exciting, 3D, eye-catching"). How to see it: `npm run dev`, then press **Splash** (or
**Splash (reduced motion)**) in the dev harness under the window's facts panel.

Tested 2026-10-18 on Windows 11, WebView2 155, Tauri 2.12.4, `three` 0.186.1, one 5120 × 1440
monitor at 100 %, refresh ~240 Hz.

## What it does

Concept from design/DESIGN.md: one particle stream per session being restored, in that session's
project colour, sweeps in from depth; the streams fly as ribbons toward the centre and condense into
a particle silhouette of the seven-bar mark (~1.3 s); the solid mark fades in under a bloom pulse
on the accent bar and turns into place in 3D (~1.2–2.5 s); the window fades out at 2.8 s. "Restoring
N of M sessions" counts up as sessions come back. Any key or click skips (180 ms fade). With
`prefers-reduced-motion` the window shows the static mark and the count for ~1 s.

Built as real P4 code in `src/splash/` (`scene.ts`, `SplashView.vue`) and `src-tauri/src/splash.rs`,
with its own capability file. Particle motion runs in the vertex shader (5,400 points, almost no
per-frame CPU); the mark's materials and the bloom pass compile in the background
(`compileAsync`), so the first frame draws only backdrop and particles. Each window imports only its
own view, so the splash loads 15 KB of view code plus the 584 KB (147 KB gzipped) three.js chunk and
none of the main window's code. In the spike, restore progress is simulated; P4 drives it from real
restore events.

## What was measured, and how

Production assets (`vite build`, served by `vite preview` to the debug binary), three runs, plus a
baseline. Times come from the splash page's own clock and from the main window's clock around the
open request.

| Measure | Result | Target |
|---|---|---|
| Open request → first WebGL frame | **155–161 ms** (66–77 ms after the splash page starts loading) | < ~300 ms |
| Finished | **2.86 s** after the page starts | ≤ 3 s |
| Splash frame times | p95 7 ms, worst 17–28 ms | smooth |
| Skip | key at 1.07 s → closed at 1.25 s | skippable |
| Reduced motion | static mark and count, closed at ~1.2 s | short static version |
| **Main window while the splash plays** | frame p95 6.5 ms (baseline 6.5 ms); IPC round trip median 1.3–1.4 ms (baseline 1.3 ms), one outlier per run of ~20 ms when the splash window is created | startup not delayed |
| Background colour after post-processing | exactly `#0a0f16`, the page backdrop (sampled pixel) | no visible jump |

Frames were captured with `PrintWindow` at fixed times for review (contact sheet in `_verify/`, not
committed).

## Findings

1. Through three.js's bloom composer, `renderer.setClearColor` comes out grey-blue (41, 57, 76 instead
   of 10, 15, 22) because it is converted twice; `scene.background` is handled correctly. A/B
   sampling with bloom and tone mapping toggled isolated it.
2. ACES tone mapping crushed the dark backdrop below the CSS one behind the canvas, which would show
   as a jump when WebGL takes over; the splash uses no tone mapping and a backdrop texture identical
   to the CSS gradient.
3. `three` ships no TypeScript types and `@types/three` is not on the approved list, so the scene is
   typed through a one-line ambient declaration. **P4 should ask to add `@types/three`.**
4. Building a window in a synchronous command deadlocks on Windows (found in S3); the splash opener
   is async.

## What it means for the plan

P4 can build the splash as designed: a separate short-lived window that opens before restore starts
and reflects it, never gating it. The open questions are taste ones for Matthew (colours, duration,
how much glow) and wiring it to real restore events.
