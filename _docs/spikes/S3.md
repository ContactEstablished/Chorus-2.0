# S3 — Fleet switcher strip

**Verdict: changed approach, then pass.** `focusable: false` alone does not stop a WebView2 window
from taking focus. With a native input shield over the web content, the strip is never activated:
clicking and dragging it leaves an external app's text box focused, and typed text still lands
there. Multi-DPI and display-change behaviour could not be tested on this machine (one monitor).

Tested 2026-10-18 on Windows 11 (build 26200), one 5120 × 1440 monitor at 100 % (96 DPI), Tauri
2.12.4 / tao 0.37.1, WebView2 155. All input was **real OS input** (`SetCursorPos` + `mouse_event`,
`SendKeys`), not DevTools events (LESSONS L10); every click was preceded by a `WindowFromPoint` check
that the point was on the intended window, and the cursor was restored afterwards.

## What was built (kept as real code for P7)

- `src-tauri/src/fleet.rs`: the `fleet` window (decorations off, always on top, no taskbar entry,
  `focused(false)`, `focusable(false)` → `WS_EX_NOACTIVATE`), created in an **async** command
  (building a window inside a synchronous command deadlocks on Windows; the first attempt hung the
  app).
- The **input shield**: a layered child window owned by Chorus (alpha 1/255: invisible but
  hit-tested) covering the strip's client area, above the WebView2 child. Its window procedure
  answers `WM_MOUSEACTIVATE` with `MA_NOACTIVATE`. On a press it follows the OS cursor in **physical
  pixels** (`GetCursorPos` → `SetWindowPos` with `SWP_NOACTIVATE`) until the button is released; a
  release within 4 px is a click, sent to the strip's page as a `fleet-click` event, where the page
  clicks the element under that point. The app manifest now declares Windows 10 (`supportedOS`),
  which layered child windows need.
- `src-tauri/capabilities/fleet.json`: the strip window gets its own capability set.
- The strip page (`src/spikes/FleetStrip.vue`, throwaway) and `?view=fleet` routing in `main.ts`.

## What was measured, and how

| Run | Foreground before → after click → after drag | Click registered | Window moved (`GetWindowRect`) |
|---|---|---|---|
| 1: `focusable(false)` only | Chorus → **Chorus fleet** → Chorus fleet | yes | 150 × 40, exact |
| 2: with the input shield | Chorus → Chorus → Chorus | yes | 150 × 40, exact |
| 3: with the shield, external app focused | S3 dictation target → same → same | yes | −60 × 40, exact |

In run 3 a separate process showed a window with a text box ("S3 dictation target", a stand-in for
the app a dictation tool types into). The test clicked into its text box, clicked the strip's
button, dragged the strip, then typed "dictated text" with real keystrokes. The text box ended with
`text=[dictated text] focused=True`.

Why run 1 failed: the strip's window tree is `Tauri Window` (Chorus) → `WRY_WEBVIEW` (Chorus) →
`Chrome_WidgetWin_0` (Chorus) → `Chrome_WidgetWin_1` (WebView2 browser process) →
`Chrome_RenderWidgetHostHWND` (WebView2). Clicks land on the last one, which is in another process
and activates its top-level ancestor regardless of `WS_EX_NOACTIVATE`.

## Not tested

- **Other DPI scales and moving between monitors.** This machine has one monitor at 100 %, and
  changing the display scale would change Matthew's session. The design is DPI-independent by
  construction (drag and hit points in physical pixels; the page divides by `devicePixelRatio`), but
  that needs a second monitor or a scale change to prove.
- **Display changes** (monitor unplugged or rearranged) need the same hardware.
- Hover effects: the page gets no pointer movement while the shield covers it. P7 can forward
  `WM_MOUSEMOVE` positions the same way as clicks if the strip needs hover states.

## What it means for the plan

P7's strip is buildable as planned, with the input shield as the way to take input (D38, proposed).
It also guards D23: the same check (click, then type into another app) belongs in P7's exit test.
The DPI and display-change checks move to P7, on hardware that has them.
