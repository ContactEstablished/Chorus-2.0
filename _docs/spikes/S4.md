# S4 — DPAPI vault

**Verdict: pass.**

Tested 2026-10-18 on Windows 11 (build 26200) with the `windows` crate 0.62.2 (`CryptProtectData`,
`CryptUnprotectData`, `BCryptHash`, `BCryptGenRandom`), Tauri 2.12.4, in the real dev app. All keys
were fake: a random `sk-or-v1-` + 64 hex digits generated inside the back end. No key was printed;
presence was proved by length and a SHA-256 prefix.

## What was built (kept as real code)

- `src-tauri/src/vault/`: `protect` / `unprotect` with DPAPI in **current-user** scope, an app-specific
  entropy (`chorus2.vault.v1`) and `CRYPTPROTECT_UI_FORBIDDEN`; `fingerprint` (first 16 hex digits of
  SHA-256, safe to show); `random_bytes` from the OS RNG. Unit tests: round trip, the blob never
  contains the plaintext, a tampered blob is refused, SHA-256 known answer.
- Launch path (`sessions/`): a spawn request may name a vault key and the variable to put it in. The
  key is decrypted at that moment, validated variable names only (upper-case, ≤ 64 characters, never
  `PATH`, `TERM` or another baseline name), and placed in the child's environment last, so nothing can
  displace it. The front end never receives a key, only labels, lengths and fingerprints.
- `chorus-core::scrub`: the stream scrubber, ported from Chorus 1 (exact vault values, longest first,
  with a held-back tail so a key split across reads is still caught) and extended with the shared key
  shapes from `secret-patterns.json` (the list `npm run grep:secrets` uses), matched without a regex
  engine. When output goes quiet with a possible key start held back, it is released after 30 ms; a
  held prefix of a known key (8+ bytes) is released as the placeholder and the rest of that key is
  dropped if it follows. 9 unit tests.
- Every session's output now passes through the scrubber before batching, with or without a key (the
  key shapes always apply).

Spike-only (removed in P1): an in-memory label → blob map, and two dev commands,
`spike_vault_add_fake_key` (returns length, blob size and fingerprint) and `spike_vault_contains`
(returns the length of the longest piece of the key found in a text, never the key).

## What was measured, and how

| Check | Result |
|---|---|
| Round trip from Rust | `cargo test`: encrypt → decrypt returns the plaintext; tampering one byte makes decryption fail. |
| Blob at rest | 73-byte key → 308-byte blob written to the dev data folder. No `sk-or` bytes in it. |
| **Key arrives in the child** | A shell launched with the key as `CHORUS_FAKE_KEY` ran PowerShell to print `$env:CHORUS_FAKE_KEY.Length` and its SHA-256 prefix: **73** and **653e6e84162c1856**, equal to the vault's own values. The variable name appeared in the session's env list; nothing else changed (10 names). |
| **Absent from argv** (LESSONS L12) | `Win32_Process` filtered by `Name` (`cmd.exe`, `powershell.exe`), sorted by `CreationDate`, argv scanned for the key's shape without printing it: **0 matches**. Argv lengths of the session's processes: `cmd.exe` 27, `powershell.exe` 46 — **identical** in a control session launched without a key. |
| **Redacted on screen** | `echo key=[%CHORUS_FAKE_KEY%]` rendered `key=[[REDACTED-CREDENTIAL]]`. The key printed in two writes 5 ms apart, and 120 ms apart (past the 30 ms release, so the idle path ran), each rendered `<<[REDACTED-CREDENTIAL]>>`. A key shape that was never in the vault (`sk-ant-…`, assembled in PowerShell) was also redacted. In every case the longest piece of the key anywhere on screen was 2–3 characters (coincidences such as `sk-`). |
| Nowhere at rest | 381 files under the dev app's Roaming and Local data (including WebView2's cache) and `_verify/` scanned as Latin-1 and UTF-16: **0** key-shaped strings. `npm run grep:secrets`: clean. |

## Notes

- Any same-user process can call `CryptUnprotectData`; the entropy only stops other apps that don't
  know it. This is the protection D5 and ARCHITECTURE §8 intend (current-user DPAPI), not more.
- A process's environment is readable by other processes of the same user, as argv is. The gain over
  argv is that the environment doesn't appear in process listings, crash reports or shell history.
- The scrubber may delay the last byte or two of output by up to 30 ms when they could start a key
  (`s`, `g`, `A`). That is under two frames and only when output pauses on such a byte.
- Residual, as in Chorus 1: a TUI that interleaves escape sequences between a key's characters
  defeats substring matching. The pinned `TERM=xterm-256color` avoids the case Chorus 1 saw.

## What it means for the plan

None of the plan changes. P1 moves the blobs into SQLite (`credentials`), adds key entry to Settings,
and keeps this launch path and scrubber; the scrubber also runs on scrollback, history rows, narrator
input and exports, as ARCHITECTURE §8 says.
