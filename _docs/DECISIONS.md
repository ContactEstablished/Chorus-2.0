# Chorus 2.0 — Decisions

Fresh numbering for 2.0. Chorus 1's roadmap decisions (D1–D17x) are referred to as "Chorus 1 D<n>".
Add new decisions at the bottom; never renumber. Status is **Decided** (Matthew agreed), **Proposed**
(recommended, awaiting his yes) or **Superseded** (replaced by the decision named).

On 2026-10-18 Matthew kept the name Chorus, accepted every default in OPEN-QUESTIONS.md, and moved voice
out of Chorus into a separate dictation app (D22–D35). What is still open is in OPEN-QUESTIONS.md.

| D40 | 2026-10-19 | **The JEV AI key is for TypeSafe's Jev API** (was Q7b). Jev is a "System One" model. It does not write text: it answers typed questions about a given state (`choice`, `score`, or a 0–1 probability called `noul`), each with calibrated probabilities, in about 70–500 ms. The call is `POST https://api.typesafe.ai/v1/systemone` with `Authorization: Bearer <key>` and model `jev-latest`. P2 stores the key in the vault, with a connection test that sends one tiny request (the docs list no free test endpoint). Jev cannot run the narrator, which needs text (D28). Where Chorus uses it is decided when each phase starts. The candidates are judging a turn's end as done, needs input or blocked (P7), ranking next steps (P6) and choosing a routing tier (P12). Each such use would sit behind a capability, with a fallback that doesn't need Jev | Decided | Matthew, 2026-10-19. API shape from docs.typesafe.ai (quick start), in early access; input costs $0.042 per million tokens |
| D41 | 2026-10-19 | **A session's child joins its Job Object just after it starts, and anything it started in that moment is adopted**, rather than atomically at `CreateProcess`. portable-pty takes no job attribute at spawn, and the stack is locked (CLAUDE.md), so P1 assigns the child right after spawning it. It then takes a process snapshot and assigns any descendant that is outside the job and was created after its parent (`chorus_core::tree::strays`). Two ways make it strictly atomic, if wanted: patch portable-pty to pass `PROC_THREAD_ATTRIBUTE_JOB_LIST` (a vendored copy with one change), or start agents through a small console launcher that waits to be put in the job before starting the agent | Decided | Matthew, 2026-10-19: keep it (option 1), rather than a patched portable-pty or a launcher. The gap is the time between `CreateProcess` returning and the assignment. Agent startup takes far longer than that before it can start anything. None escaped in S1 or P1 |
| D42 | 2026-10-19 | **Each opencode run is `opencode serve` plus `opencode attach`, and its options are the server's configuration.** The server is a hidden child in the run's job, on `127.0.0.1` with a random password that only the two processes' environment carries (and that the scrubber redacts). Chorus creates the opencode session through the API on the first run and attaches to it after that, which is how Restart resumes. Model, effort and permission go in `OPENCODE_CONFIG_CONTENT`. An effort needs a model, because opencode drops a variant that isn't beside the turn's model. A chosen model is checked against the server's list, and a missing variant, provider or key is noted on the session. What each turn really ran with is read back every 3 s and shown, with any difference from what was asked (P3 moves this to server events). Permissions: Manual and Accept edits are `permission` rules, Plan is the `plan` agent, Full access is `"allow"`. There is no Auto. Each session keeps its own opencode state and data folders under Chorus's data (as in P1), so it doesn't see the user's own opencode logins or conversations, and keys come from the vault. Chorus deletes the TUI's remembered `model.json` before each run that sets a model or effort | Proposed | Measured on 1.19.3 (LESSONS L35): the attached TUI ignores a session's stored model, and its remembered variant beats configuration (L5). Reading back is the only proof an effort applied |

Grok: Deep, and a permission mode always passed (Auto by default), because a user config can set `always-approve`. opencode: none. **Codex's conversation is found through `CODEX_INTERNAL_ORIGINATOR_OVERRIDE=chorus-v2-<session>`**, which Codex writes into the rollout. The variable is undocumented but present in 0.162.1. | D45 | 2026-10-19 | **Providers are OpenRouter, OpenAI-compatible gateways and Jev, each pointing at keys in the vault; a session can run on one.** Codex runs on OpenRouter or a gateway, through `-c model_provider=…` overrides with the Responses wire API, as Chorus 1 measured. opencode runs on OpenRouter, through `OPENROUTER_API_KEY` and an `openrouter/<id>` model; Chorus declares the model in its configuration with the catalog's efforts as variants, so models newer than opencode's own list still run. Claude Code (its login or an Anthropic key), Grok (no setting for another address) and opencode on a gateway are refused with the reason, for now. **With a management key, every run gets its own OpenRouter key**: capped at the provider's limit (default $1, because OpenRouter holds back a request's full output cost), expiring within a day, revoked when the run ends, when Chorus quits, or at the next start-up, and costed from analytics after revoking (LESSONS L16). Without one, runs use the normal key, uncapped, and the session says so. A failed mint falls back to the normal key and says so. The minted key is only ever in the child's environment and the scrubber's list; the ledger keeps OpenRouter's hash of it. The catalog is fetched when the user asks, and the shortlist is what the launch form offers | Proposed | Chorus 1's measured routes and capped-key lifecycle (`openrouterKeys.ts`, `codex.ts`, `opencode.ts`), re-checked against OpenRouter's key API and its public catalog on 2026-10-19 |
| D46 | 2026-10-19 | **P3's agent events only observe.** Hooks post to a loopback listener (axum, port chosen at start) with a per-run token that only the agent's environment holds, and every accepted post gets an empty 204, sent after the event is written. Claude Code gets an HTTP hook per event from a settings file in Chorus's data. Codex gets a command hook per event running the std-only `chorus-hook` relay, which the dev command builds beside `chorus.exe`; **bundling it in the installer is still to do** (the release build's `beforeBuildCommand` and Tauri's `externalBin`). opencode's events come from its server's stream.
